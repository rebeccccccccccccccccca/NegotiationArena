# 政府採購案例資料

議價情境的品項、數量與預算取自真實的政府財物採購決標公告。本資料夾是抓取、抽樣、篩選的結果；程式在 `experiments/procurement/`。

## 資料來源

| 項目 | 內容 |
|---|---|
| 原始來源 | 行政院公共工程委員會「政府電子採購網」決標公告，https://web.pcc.gov.tw |
| 取得管道 | g0v 社群「標案資料 API」，https://pcc-api.openfun.app（志工維運的第三方彙整；後端程式 https://github.com/ronnywang/pcc.g0v.ronny.tw，BSD 授權） |
| 標的分類代碼表 | 政府資料開放平臺資料集 6576「政府電子採購網採購標的分類」，https://web.pcc.gov.tw/osm/public/proctrg/download/CpcOpenData.xml |
| 抓取日期 | 抽樣框架 2026-10-16；明細的起訖時間見 `MANIFEST.json` 的 `details.fetched_from` / `fetched_to` |

原本規劃的 data.gov.tw 資料集 900002（決標）、900001（招標）實際上是 opendatatw.org 的鏡像編號。data.gov.tw 上的原頁面已無法開啟，而且招標資料只有 6 個欄位、沒有預算金額，無法用案號串接取得預算，所以改用上面的 API。API 的單一筆決標公告同時包含預算、底價、決標金額、品項與數量，不需要串接。

論文引用時，政府電子採購網與 g0v API 兩者都要列出，並寫明抓取日期。

## 授權與使用條款

- **政府電子採購網著作權聲明**（https://web.pcc.gov.tw/pis/prac/declarationClient/right ，更新日期 105/02/19）：
  - 依著作權法第 9 條不得為著作權標的的內容，任何人都可以自由利用。
  - 其餘內容在報導、評論、教學、研究等正當目的下，可以在合理範圍內引用，但要註明出處。
- **g0v 標案資料 API**：API 首頁要求資料利用遵循上述原始來源的著作權聲明；商業利用請改用採購網官方的開放資料。
- **標的分類代碼表**：政府資料開放授權條款第 1 版（https://data.gov.tw/license）。
- **個人資料**：原始公告含機關聯絡人姓名、電話與廠商名稱。原始檔（`raw/`）不進版控、不公開；解析後的 CSV 不含聯絡人欄位。

## 抽樣框架與抽樣

- **框架**：「決標公告日期」介於 2025-10-01 至 2026-09-30 的所有決標公告，共 172,290 筆。
  - 依據的是**公告日期，不是決標日期**；決標日期另存於 `award_date` 欄。
  - 只含「決標公告」，不含無法決標公告與更正公告。
- **查無公告的平日**：共 18 天。除了 2026-06-24（週三）以外，都對應國定假日（中秋、國慶、光復節、行憲紀念日、元旦、春節、和平紀念日、清明、勞動節、端午、教師節）。2026-06-24 原因不明，可能是 API 漏抓。清單見 `MANIFEST.json` 的 `frame.weekdays_without_notices`。
- **每月框架筆數**：

  | 年月 | 筆數 | 年月 | 筆數 |
  |---|---|---|---|
  | 2025-10 | 12,051 | 2026-04 | 13,410 |
  | 2025-11 | 12,722 | 2026-05 | 13,032 |
  | 2025-12 | 23,559 | 2026-06 | 13,249 |
  | 2026-01 | 20,154 | 2026-07 | 15,442 |
  | 2026-02 | 9,309 | 2026-08 | 13,068 |
  | 2026-03 | 13,878 | 2026-09 | 12,416 |

- **抽樣方法**：依公告月份分層。每月先把該月公告依檔名固定排序，再以種子 20261016 隨機排列，取前 250 筆，12 個月共 3,000 筆（`sample_ids.csv`）。
  - 每月取同樣筆數，因此 12 月（年底消化預算）在樣本中的比重低於框架中的比重。
  - **擴大抽樣**：用同一個種子、取更大的每月筆數即可。原樣本會完整保留，只會在後面追加。

## 篩選規則

依下表順序檢查；每筆公告標記第一個沒通過的規則（`awards_parsed.csv` 的 `exclude_reason`），觸發的欄位或關鍵字記在 `exclude_detail`。

| 順序 | 規則 | 判斷依據 | 誤判風險 |
|---|---|---|---|
| 1 | 非財物類 | 標的分類 | 低（結構化欄位） |
| 2 | 預算或決標金額缺漏 | 預算／總決標金額「是否公開」與數值 | 低 |
| 3 | 複數決標 | 「是否複數決標」欄位，或第 1 品項有多家得標廠商 | 低 |
| 4 | 共同供應契約／開口契約 | 「是否屬共同供應契約採購」欄位；標題含「開口契約」「開口合約」 | 關鍵字部分中等 |
| 5 | 租賃、維護、軟體類 | 標題或品項名稱含租賃、租用、承租、租購、標租、維護、維修、保養、修繕、軟體、授權、訂閱 | **中高**（純關鍵字） |
| 6 | 藥品、國防 | 分類代碼 352（醫藥產品，含部分檢驗試劑）、447（武器彈藥）；「涉及國家安全」欄位為是；機關名稱含國防部、陸軍、海軍、空軍、憲兵、軍備局 | **中高**（國安欄位會排除非國防案，例如議會監視器） |
| 7 | 標的資訊不足 | 決標品項數不是 1、缺品項名稱或數量；標題含「等 N 項」 | 中 |
| 8 | 決標金額高於預算 | 決標 > 預算，視為資料異常 | 低 |
| 9 | 品項不在白名單 | `pool_rules.json` 的 `category_whitelist`（標的分類代碼前綴） | 無（研究者設定的範圍） |
| 10 | 預算超出金額範圍 | `pool_rules.json` 的 `amount_tiers`（採購金額級距）、`budget_min`／`budget_max` | 無（研究者設定的範圍） |

規則 1–8 是基本篩選，規則 9–10 是研究範圍設定，詳見下一節。

## 研究範圍設定（`pool_rules.json`）

所有會影響候選池的設定都集中在 [pool_rules.json](pool_rules.json)，不放在命令列參數，這樣凍結的版本只有一份。

| 設定 | 意思 | 例子 |
|---|---|---|
| `seed` | 合格案例隨機排序的種子 | `20261016` |
| `roles` | 角色與筆數，依序分配 | `"calibration:10,stage1_2:40,stage3:40,wording:20,reserve:10"` |
| `category_whitelist` | 品項白名單，標的分類代碼前綴；空清單表示不限 | `["452", "45"]`：`"452"` 只含該代碼，`"45"` 含 45 底下所有代碼 |
| `amount_tiers` | 允許的採購金額級距；空清單表示不限 | `["未達公告金額"]` |
| `budget_min` / `budget_max` | 預算金額上下限（新臺幣），`null` 表示不限 | `300000` / `3000000` |
| `frozen` | 是否凍結 | `false` |

**目的**：
- **品項範圍**：只留性質相近的幾類（建議依官方分類代碼挑 2–4 類），讓模型對「買什麼」的先備知識差距小。
- **金額範圍**：避免幾萬和幾千萬的案件混在一起，建議最高／最低預算比不超過約 10 倍。

**級距與預算上下限要一起用**：
- 只限定一個級距通常不夠。依目前資料，「公告金額以上未達查核金額」這個級距內的預算就從 110 萬到 7,350 萬，相差約 67 倍，所以要用 `budget_min`／`budget_max` 才能壓到 10 倍以內。
- 兩者不能互相矛盾，也不要把適用不同採購程序的級距混在一起。`build_pool` 會在兩種情況提示：
  - 選定的級距在預算範圍內沒有任何案例（設定矛盾）。
  - 合格案例橫跨多個級距。
- `build_pool` 每次執行也會印出合格案例預算的最高／最低比，以及 p95／p05 比。

**選擇依據**：白名單與金額範圍只能依兩件事決定：
1. 資料分布：`category_summary.csv`、`category_group_summary.csv`。
2. 品項是否有共同主題。

**不能依議價前導的結果調整**。

**挑選依據**：`build_pool` 會輸出兩個檔：
- `category_summary.csv`：每個分類代碼一列
- `category_group_summary.csv`：每個 2 位數大類一列

兩檔第一列「ALL」是整體數字。欄位包括：通過基本篩選（規則 1–8）的案例數 `n_passed_base`、套用範圍設定後的合格數 `n_eligible`、預算的最小值／25%／中位數／75%／最大值，以及各金額級距的筆數。

**合格案例不足時，先擴大抽樣，不放寬範圍**：範圍是研究設計的決定，抽樣量只是資料量。
- 程式會依目前合格率，估算需要的樣本數與每月筆數（另附加 25% 餘裕的版本）。
- 擴大抽樣會保留原樣本、只在後面追加，不用重抓。
- 只有在擴大抽樣不可行時，才參考程式附帶列出的放寬結果，順序是先放寬金額、再放寬品項。

**凍結時機與範圍**：
- 必須在正式實驗前完成，而且要在看到任何正式議價結果之前。
- 本檔的種子、角色分配、品項白名單、金額範圍，屬於研究整體「凍結清單」的一部分。凍結清單的其他項目是：價格比例規則、提示詞版本、施壓句庫、回合上限、模型與推理強度、案例數與條件配置。

**凍結程序**：
1. 決定白名單、金額範圍與角色，寫進 `pool_rules.json`，並把 `frozen` 改成 `true`。
2. 執行 `build_pool`，產生最終的 `candidates.csv`。
3. 執行 `fetch_awards manifest`。`MANIFEST.json` 的 `pool_rules` 會記錄設定檔全文與 SHA-256。
4. commit，並打 git tag（例如 `data-v1`）。

凍結後若 `pool_rules.json` 與 MANIFEST 記錄的雜湊值不同，`build_pool` 會拒絕執行。要修改就必須刻意解除凍結並重新記錄，修改會留在 git 歷史中。

**人工核對**：規則 4–6 依賴關鍵字或機關名稱。`validate_rules.py draw` 會從這幾條規則適用的母體（財物類、金額公開、非複數決標）分層隨機抽 50 筆：被排除、被保留各 25 筆。人工填寫 `human_reason` 後執行 `score`，即可得到：
- 精確率（被排除者中確實該排除的比例）
- 陰性預測值（被保留者中確實該保留的比例）
- 依母體大小加權的整體準確率，以及估計的召回率

這些數字可以寫進方法章。

## 角色分配

合格案例依 `pool_rules.json` 的種子（20261016）固定隨機排序（`pool_rank`），再依 `roles` 的順序分配角色。預設為：

| 角色 | 筆數 | 用途 |
|---|---|---|
| calibration | 10 | 前導校準，不與正式案例重疊 |
| stage1_2 | 40 | 階段一、階段二共用 |
| stage3 | 40 | 階段三，與階段二不同案例 |
| wording | 20 | 措辭穩健性 |
| reserve | 10 | 備用 |
| pool | 其餘 | 未分配 |

合計需要 120 筆合格案例。校準排在最前面，所以之後改變任何階段的案例數，都不會讓案例移進或移出校準組。若階段一、二要用不同案例，把 `pool_rules.json` 的 `roles` 改成 `"calibration:10,stage1:40,stage2:40,stage3:40,wording:20,reserve:10"`，這樣需要 160 筆。

## 比例的解讀

- **預算**與**底價**都是採購機關自己設定的，屬於買方側。底價是機關的價格上限，概念上比較接近買方的 B，不是賣方成本 C。
- **決標金額**是實際成交價，只能作為「成交價的參考」。
- **賣方成本 C 沒有可直接對應的真實資料**。C 是依比例規則假設的，`ratio_summary.csv` 的分布只用來讓比例貼近真實。

## 已知限制

- **案例偏向單純採購**：篩選後的案例偏向單一品項、資訊完整、決標不高於預算的標案。每一步排除的筆數見 `exclusion_counts.csv`。
- **只含有成交的案件**：樣本是決標公告，不含無法決標或廢標的案件，所以成交價分布是「有成交」條件下的分布。
- **抽樣比重**：每月等量抽樣，所以 12 月的比重低於它在框架中的實際比重。
- **規則誤判**：規則 4–6 有漏判與誤判，以人工核對的結果報告準確率。
- **API 可靠性**：API 為第三方彙整，可能有漏抓（例如 2026-06-24），之後也可能改版或下線。原始檔已備份，並在 `MANIFEST.json` 記錄 SHA-256 雜湊值。
- **抓取速度**：API 有速率限制。每秒 1 次請求時，約三分之一會收到 429（請求過多），因此預設間隔改為 2 秒。遇到 429 時程式會等待後重試，不會遺漏資料。
- **範圍設定的代價**：品項白名單與金額範圍會讓案例更同質，但也讓結論只適用於所選品項與金額範圍。

## 重現步驟（在專案根目錄）

```
.venv\Scripts\python -m experiments.procurement.fetch_awards all        # 分類表、框架、抽樣、明細（可中斷續跑）
.venv\Scripts\python -m experiments.procurement.build_pool              # 篩選、分類統計、候選池、比例分布（設定讀 pool_rules.json）
.venv\Scripts\python -m experiments.procurement.validate_rules draw     # 人工核對樣本
.venv\Scripts\python -m experiments.procurement.validate_rules score    # 人工填寫後計分
.venv\Scripts\python -m experiments.procurement.fetch_awards manifest   # 備份到 backups/，並把雜湊值與 pool_rules.json 寫入 MANIFEST.json
```

擴大抽樣：

```
.venv\Scripts\python -m experiments.procurement.fetch_awards sample --force --per-month 400
.venv\Scripts\python -m experiments.procurement.fetch_awards details
```
